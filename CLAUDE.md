# DPS Aion

Static site (Vercel, https://dpsaion.vercel.app/) with the raid history of Cry's group in Aion 2, built from the Questlog desktop app's combat meter. The user writes in Spanish; commit messages are in Spanish. The site is bilingual (es/en): `assets/i18n.js` holds every UI string in both languages (`data-i18n` attributes in HTML, `I18N.t()` in JS) and the ES | EN toggle; never hardcode UI text in `raid.js` / `home.js`.

## Layout

- `index.html` + `assets/home.js` — home: list of raids from `raids/index.json`, best attempt per boss over time, the 5 players with most raids (ties: most recent) and a player search. Search results have a "request my profile analysis" button that POSTs `{ slug }` to `api/solicitar.js` (Vercel function), which posts the player's metrics to Discord through the `DISCORD_WEBHOOK_URL` env var set in Vercel. When the user forwards a request, write or refresh that player's `perfil.json` / `perfil.en.json`.
- `raids/<slug>/` — one folder per raid: `index.html` (copy of `assets/raid-shell.html`), `data.json` (stats), `analisis.json` (Claude's text).
- `assets/raid.js` — renders a raid page from `data.json`, the analysis and the names for the current language (`analisis.json` / `analisis.en.json`, `nombres.json` / `nombres.en.json`). Clicking a player opens their card (ficha) with skill icons from cdn.questlog.gg.
- `nombres.json` (es) and `nombres.en.json` (en) — names for skill and NPC ids, filled by `tools/actualizar-nombres.ps1 -Idioma es|en` from questlog.gg for every id in the raids (data.json plus, from the database, the group's heals, shields and damage taken), plus `iconos` (icon paths) (`combatLog.entities.skills` / `.names`, the same source as the Questlog app). `habilidades` and `npcs` are regenerated; `apodos` are hand-written labels that win over them (most boss attacks are just "Ataque" in game data, so they show as "Ataque <id>" unless they have an apodo). NPCs named `N_Invisible_Summon_*` are invisible damage zones spawned by boss skills, not adds: they show as "Zona 8-2" etc.
- `tools/extraer-raid.ps1` — updates the database (`cargar-db.ps1`, skip with `-SinCargar`), picks the run (by default the latest with 8+ players, i.e. a raid; `-Lista` shows recent runs, `-Run <id prefix>` picks one, `-Jefe <npc>` the boss) and writes `raids/<slug>/data.json` with `db/raid.sql`, plus the index entry. Every `.ps1` must stay UTF-8 with BOM (Windows PowerShell 5.1); `tools/duckdb.ps1` holds the shared DuckDB helpers.
- `jugadores/<slug>/` — one profile per player across all published raids: `data.json` (built by `tools/perfiles.ps1`, which `extraer-raid.ps1` runs after every extraction or `-Reindexar`), `index.html` (copy of `assets/jugador-shell.html`) and `perfil.json` / `perfil.en.json` (Claude's written profile: `actualizado`, `raids`, `resumen`, `fortalezas`, `mejorar`, `recomendaciones`). `assets/jugador.js` also computes an automatic profile from the numbers. Below the profile, tabs (Evolución, Supervivencia, Curación y apoyo, Daño, Rotación, Sus raids; the tab is in the `#hash`) hold the deep-dive, each number compared with the player's class in that raid (`clase_media`) or the group (`grupo_media`). Supervivencia, Curación y apoyo and Rotación use `detalle.<player>.apoyo` / `.supervivencia` / `.rotacion` (casts per minute alive, idle time, first hit on the boss, casts by skill, buffs given to the group with their uptime) and the `vida_5s`/`vida_1s`/`dano_5s`/`cura_5s` fields of each death, which only raids extracted from the database since 2026-11-08 have (the earlier raw data was lost when the PC was formatted); for older raids those tabs show a notice.
- `db/` — local DuckDB database with every event Questlog records (hits, heals, shields, damage taken, buffs, HP over time, deaths, resurrections, boss casts, runs with builds). `tools/cargar-db.ps1` copies new Questlog files to `db/archivo/` (Questlog keeps only the last 500 encounters and deletes older ones; the archive keeps them) and loads what is missing into `db/aion.duckdb`; `-Reconstruir` rebuilds it from the archive. Schema in `db/esquema.sql`, loaders `cargar*.sql`, views in `db/vistas.sql` (`intentos`, `grupo`, `jugador_intento`, `muertes_intento`, `jefe_enc`, macros `nombre_hab()` / `nombre_npc()`), which follow the same rules as `db/raid.sql` (the generator of `data.json`). After changing `raid.sql` or the loaders, regenerate and compare with the committed files: `tools/comparar-json.ps1 old.json new.json -Ignorar meta.extraido -SinOrden dps_intento,causas` (ties in sorted lists may swap). In `usos` each skill appears in variants: the cast has a spec suffix >= 100 (14050340) or a multiple of 10 (stigmas, 14380030), small suffixes (14050008) are effects that trigger on their own, and `parada = 'cancelled'` (only on the recording character) is an animation-cancelled cast that did hit; this rule is inferred from the data. Group variants into the base skill with `(id // 10000) * 10000`. Times are ms from the start of the encounter; join events to players through `jugador_intento.entidad`. Query with `tools/consulta.ps1 "select …"`. The database and archive are git-ignored (they include players outside the group).
- `nueva-raid.bat` — the user's button: pull, extract the latest raid, refresh names, update the database, commit, push. Vercel deploys on push.

## "Analiza la última raid"

1. If the newest run in Questlog is not in `raids/index.json` yet, run `tools/extraer-raid.ps1` (or ask the user to press `nueva-raid.bat`).
2. Read `raids/<slug>/data.json` and query `db/aion.duckdb` for anything deeper (healing by skill, buffs, HP before each death, resurrections). Look at: progress per attempt and where attempts stall (`curva`), what kills people (`causas`, one-shots are `golpe_max` >= 100000), the boss cast timeline (`casteos`), stagger breaks (`intentos.rotura_s`), each player's numbers and `detalle` (skills, damage taken, deaths with health 5 s / 1 s before, healing by skill and target, shields, mitigated and avoided hits, time below 30 % health, resurrections). Compare with earlier raids of the same boss in `raids/index.json` when there are any.
3. Write `raids/<slug>/analisis.json`:

```json
{
  "pendiente": false,
  "titular": "One or two sentences with the takeaway; **bold** is allowed.",
  "zonas": { "muro": [35, 50], "ventana": [140, 175] },
  "recomendaciones": [{ "titulo": "Short imperative.", "texto": "Why, with the evidence from the data." }],
  "jugadores": { "PlayerName": ["Personal recommendation backed by their numbers."] },
  "notas": [{ "termino": "Label", "texto": "Extra caveat about this raid." }]
}
```

   `zonas` is optional (bands on the charts: `muro` = % of boss HP, `ventana` = seconds). Give every player in `meta.grupo` at least one recommendation, based on their own data (deaths and what caused them, DPS vs the group, skill mix, damage taken), constructive and specific.
4. Write the same analysis in English to `raids/<slug>/analisis.en.json` (same structure, translated text, same ids and numbers). Without it the English page shows the Spanish text with a notice.
5. Rebuild the index and player profiles (`tools/extraer-raid.ps1 -Reindexar`).
6. Update `jugadores/<slug>/perfil.json` and `perfil.en.json` for every player in the raid with what the new night adds (trends versus their earlier raids, recurring causes of death), keeping it short and backed by `jugadores/<slug>/data.json`. Do not assume anyone's gender. Commit and push.

In analysis text, write skill and NPC ids as bare numbers (e.g. 1802880): the page replaces them with «name» from `nombres.json`, titles included. Facts must come from the data files; say so when something is an inference (for example, players who left mid-run).

Antes de escribir código de Next lee `AGENTS.md`: Next 16 cambia APIs (por ejemplo, `proxy.ts` en vez de middleware) y la documentación de la versión instalada está en `node_modules/next/dist/docs/`.

- Node: `"C:\Program Files\nodejs"` (añádelo al PATH en cada shell). Comprobar todo: `npm run typecheck && npm run lint && npm test && npm run build`.
- Idiomas: `app/[lang]`, `proxy.ts` y `lib/i18n` (ADR 0001). Los textos se sacan de `assets/i18n.js` con `npm run textos`; nunca se escriben textos de interfaz a mano en los componentes.
- La web estática (`index.html`, `assets/`, `raids/`, `jugadores/`, `api/`) sigue en el repo hasta el corte (fase 9), y ESLint la ignora.
- Base de datos: Postgres en Neon con Drizzle (`lib/db/schema/`, migraciones en `drizzle/`). En local, `.env.local` apunta a la rama **dev** de Neon (no es producción); las variables de Neon en Vercel son *Sensitive* y `vercel env pull` no las trae. Cambiar el esquema: editar `lib/db/schema/*` → `npm run db:generar -- --name <cambio>` → `npm run db:migrar` (rama dev). En Vercel las migraciones corren en el build (`npm run build:vercel`).
- Cuentas: Better Auth con Discord (`lib/auth/`, ADR 0002). La sesión se lee con `usuarioActual()` dentro de `<Suspense>`. Permisos: `lib/permisos.ts` (puro) y `lib/db/grupos.ts`; las páginas no deciden permisos por su cuenta.
- Pruebas: `npm test` (unitarias; las de integración se saltan sin base). Con la rama dev: `node --env-file=.env.local node_modules/vitest/vitest.mjs run`.
- El panel del navegador integrado, cuando está oculto, no ejecuta `requestAnimationFrame`, y React deja el contenido de los `<Suspense>` sin colocar («Loading…»). No es un fallo de la app: comprobarlo con el panel visible o forzando `$RV($RB)`.
- Probar páginas con sesión sin usar la cuenta de nadie: crear en la rama dev un usuario `prueba-*` con una fila en `session` y firmar la cookie como Better Auth (`token + "." + base64(HMAC-SHA256(token, AUTH_SECRET))`, con encodeURIComponent). Con `next start` (producción) la cookie se llama `__Secure-better-auth.session_token`, también en localhost. Al acabar, borrar `prueba-%` de `grupos` y `user`, y cerrar sesión con `POST /api/auth/sign-out`: el servidor reescribe las cookies como httpOnly, y la caché de sesión mantiene viva una sesión borrada hasta 5 minutos.

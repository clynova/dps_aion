# DPS Aion

Next.js app (Vercel, https://dpsaion.vercel.app/) with the raid history of Aion 2 groups, built from the Questlog desktop app's combat meter. Cry's group is `randoms` (https://dpsaion.vercel.app/g/randoms). The user writes in Spanish; commit messages are in Spanish. The site is bilingual (es/en): every UI string lives in `lib/i18n/es.json` / `en.json`; never hardcode UI text in components. Until 2026-11-09 it was a static site with one folder per raid; that is gone from the repo (it is in git history before commit 5394ff4).

## Layout

- `app/` (pages and API), `components/`, `lib/` — the app. Raids, analyses, profiles, names and groups live in Postgres (Neon). Technical details per module are in the section below.
- `nombres.json` (es) and `nombres.en.json` (en) — the **seed** of skill and NPC names: `habilidades`, `npcs`, `iconos` (from questlog.gg, `combatLog.entities.skills` / `.names`) and `apodos`, hand-written labels that win over them (most boss attacks are just "Ataque" in game data, so they show as "Ataque <id>" unless they have an apodo). Applied to the database on every deploy. NPCs named `N_Invisible_Summon_*` are invisible damage zones spawned by boss skills ("Zona 8-2"), `M_Summon_*` are summoned minions ("Esbirro invocado"). To add an apodo, edit both files and deploy.
- `tools/extraer-raid.ps1` — updates the local database (`cargar-db.ps1`, skip with `-SinCargar`), picks the run (by default the latest with 8+ players, i.e. a raid; `-Lista` shows recent runs, `-Run <id prefix>` picks one, `-Jefe <npc>` the boss) and writes the raid JSON with `db/raid.sql` to `%TEMP%\dps-aion\<slug>.json` (last line of its output). Every `.ps1` must stay UTF-8 with BOM (Windows PowerShell 5.1); `tools/duckdb.ps1` holds the shared DuckDB helpers.
- `tools/publicar.ps1` — publishes with the group token (saved with `-Configurar` in `%APPDATA%\dps-aion\config.json`, encrypted): a raid (runs `extraer-raid.ps1`; `-Run`, `-Archivo`, `-Visibilidad`, `-Reemplazar`), then the names questlog.gg has for its ids; `-Analisis a.json,a.en.json` and `-Perfil p.json,p.en.json` for Claude's texts; `-Nombres` for missing names only. Never print or paste a token.
- `nueva-raid.bat` — the user's button: `publicar.ps1` for the latest raid. No git: the site reads from the database.
- `db/` — local DuckDB database with every event Questlog records (hits, heals, shields, damage taken, buffs, HP over time, deaths, resurrections, boss casts, runs with builds). `tools/cargar-db.ps1` copies new Questlog files to `db/archivo/` (Questlog keeps only the last 500 encounters and deletes older ones; the archive keeps them) and loads what is missing into `db/aion.duckdb`; `-Reconstruir` rebuilds it from the archive. Schema in `db/esquema.sql`, loaders `cargar*.sql`, views in `db/vistas.sql` (`intentos`, `grupo`, `jugador_intento`, `muertes_intento`, `jefe_enc`, macros `nombre_hab()` / `nombre_npc()`), which follow the same rules as `db/raid.sql` (the generator of the raid JSON). The views only see raids in the local `raids` table, which `extraer-raid.ps1` fills with each raid it extracts; for anything else query the base tables (`encuentros`, `jugadores`, `golpes`…). After changing `raid.sql` or the loaders, run `npm run sql` and compare old and new JSON with `tools/comparar-json.ps1 old.json new.json -Ignorar meta.extraido -SinOrden dps_intento,causas` (ties in sorted lists may swap). In `usos` each skill appears in variants: the cast has a spec suffix >= 100 (14050340) or a multiple of 10 (stigmas, 14380030), small suffixes (14050008) are effects that trigger on their own, and `parada = 'cancelled'` (only on the recording character) is an animation-cancelled cast that did hit; this rule is inferred from the data. Group variants into the base skill with `(id // 10000) * 10000`. Times are ms from the start of the encounter; join events to players through `jugador_intento.entidad`. Query with `tools/consulta.ps1 "select …"`. The database and archive are git-ignored (they include players outside the group).
- Player pages (`/jugadores/<slug>`) are computed from all the player's raids (`lib/perfil/construir.ts`): the numbers, «En resumen» (Claude's summary and first 3 recommendations), an automatic profile and tabs (Perfil, the default one with Claude's text and the automatic profile, Evolución, Supervivencia, Curación y apoyo, Daño, Rotación, Sus raids) that compare each number with the player's class in that raid or the group. Supervivencia, Curación y apoyo and Rotación need `detalle.<player>.apoyo` / `.supervivencia` / `.rotacion` and the `vida_5s`/`vida_1s`/`dano_5s`/`cura_5s` fields of each death, which only raids extracted since 2026-11-08 have; older raids show a notice.

## "Analiza la última raid"

Work in a scratch folder (never in the repo) and publish with `tools/publicar.ps1`.

1. If the newest raid is not on https://dpsaion.vercel.app/g/randoms yet, run `tools/publicar.ps1` (or ask the user to press `nueva-raid.bat`). It prints the raid URL; the slug is its last part.
2. Get the raid JSON: `%TEMP%\dps-aion\<slug>.json` right after extracting it, or `GET https://dpsaion.vercel.app/api/v1/grupos/randoms/raids/<slug>` (public raids need no token). Query `db/aion.duckdb` for anything deeper (healing by skill, buffs, HP before each death, resurrections). Look at: progress per attempt and where attempts stall (`curva`), what kills people (`causas`, one-shots are `golpe_max` >= 100000), the boss cast timeline (`casteos`), stagger breaks (`intentos.rotura_s`), each player's numbers and `detalle` (skills, damage taken, deaths with health 5 s / 1 s before and their `repaso` (the last 10 s: health readings, hits, healing received, teammates and healers alive, self-shields available; the page section «Repaso de las muertes» sorts each death into one hit / burst / worn down — an inference, say so), healing by skill and target, shields, mitigated and avoided hits, time below 30 % health, resurrections), the section «Contra el mejor intento» (each attempt against the kill or the furthest one at equal progress: where it falls behind, by deaths or by pace, who was already dead, what killed them; an inference with fixed thresholds, `lib/raids/intentos.ts`), `buffs_recibidos` (share of their time alive each player had each teammate buff, against the others who get it from the same caster: whoever gets much less is probably out of range, e.g. the main healer behind the tank, so do not blame their DPS without looking at it; an inference), `especializaciones` (spec options per skill, inferred from the cast id; compare within a class, never attribute DPS to an option), and `mecanicas` (per boss attack: how many times it went out, `olas`, and for each player how many of those hit them, out of the times they were alive, `expuesto`; the page section «Fallos de mecánica» shows who takes hits the rest avoid — it is an inference, say so, and do not blame the fixed target of an attack). Compare with earlier raids of the same boss (listed on the group page and together on the boss page `/g/randoms/jefes/<npc>`, which also shows where attempts get stuck and which attacks come out at a fixed % of health; fetch them with the same GET): the raid page has a section «Desde la raid anterior» that measures each recommendation of the previous analysis by the attacks it named (so write attack ids in recommendation titles and texts), and the new analysis should say what improved and what did not instead of repeating advice already fulfilled.
3. Write `<scratch>/<slug>/analisis.json` (the folder name is the slug `publicar.ps1` uses):

```json
{
  "pendiente": false,
  "titular": "One or two sentences with the takeaway; **bold** is allowed.",
  "zonas": { "muro": [35, 50], "ventana": [140, 175] },
  "one_shot": 100000,
  "recomendaciones": [{ "titulo": "Short imperative.", "texto": "Why, with the evidence from the data." }],
  "jugadores": { "PlayerName": ["Personal recommendation backed by their numbers."] },
  "notas": [{ "termino": "Label", "texto": "Extra caveat about this raid." }]
}
```

   `zonas` is optional (bands on the charts: `muro` = % of boss HP, `ventana` = seconds). `one_shot` is optional: the hit size the raid page marks as "kills in one hit" (default 100000). Give every player in `meta.grupo` at least one recommendation, based on their own data (deaths and what caused them, DPS vs the group, skill mix, damage taken), constructive and specific.
4. Write the same analysis in English to `<scratch>/<slug>/analisis.en.json` (same structure, translated text, same ids and numbers). Without it the English page shows the Spanish text with a notice.
5. Publish both: `tools/publicar.ps1 -Analisis <scratch>\<slug>\analisis.json,<scratch>\<slug>\analisis.en.json`. Claude's analysis replaces the automatic DeepSeek one.
6. For every player in the raid, write `<scratch>/<player-slug>/perfil.json` and `perfil.en.json` (`actualizado`, `raids`, `resumen`, `fortalezas`, `mejorar`, `recomendaciones`) with what the new night adds (trends versus their earlier raids, recurring causes of death), short and backed by their numbers on `/jugadores/<player-slug>`. Do not assume anyone's gender. Publish with `tools/publicar.ps1 -Perfil …`.

In analysis text, write skill and NPC ids as bare numbers (e.g. 1802880): the page replaces them with «name», titles included. Facts must come from the data; say so when something is an inference (for example, players who left mid-run).

## La app (Next.js)

Plan e historia: `docs/plan-refactor-next.md` (fases y criterios de hecho; el corte de la fase 9 se hizo el 9/11/2026) y decisiones en `docs/adr/`. Se trabaja en `main`, en esta carpeta (`nueva-raid.bat` ya no hace git). Antes de escribir código de Next lee `AGENTS.md`: Next 16 cambia APIs (por ejemplo, `proxy.ts` en vez de middleware) y la documentación de la versión instalada está en `node_modules/next/dist/docs/`. Producción: la base de Neon es la misma para Preview y Production; para leer una preview protegida, `MSYS_NO_PATHCONV=1 vercel curl <ruta> --deployment <url>`.

- Node: `"C:\Program Files\nodejs"` (añádelo al PATH en cada shell). Comprobar todo: `npm run typecheck && npm run lint && npm test && npm run build`.
- Idiomas: `app/[lang]`, `proxy.ts` y `lib/i18n` (ADR 0001). Los textos están en `lib/i18n/es.json` y `en.json`; nunca se escriben textos de interfaz a mano en los componentes.
- Base de datos: Postgres en Neon con Drizzle (`lib/db/schema/`, migraciones en `drizzle/`). En local, `.env.local` apunta a la rama **dev** de Neon (no es producción); las variables de Neon en Vercel son *Sensitive* y `vercel env pull` no las trae. Cambiar el esquema: editar `lib/db/schema/*` → `npm run db:generar -- --name <cambio>` → `npm run db:migrar` (rama dev). En Vercel las migraciones corren en el build (`npm run build:vercel`).
- Cuentas: Better Auth con Discord (`lib/auth/`, ADR 0002). La sesión se lee con `usuarioActual()` dentro de `<Suspense>`. Permisos: `lib/permisos.ts` (puro) y `lib/db/grupos.ts`; las páginas no deciden permisos por su cuenta.
- Pruebas: `npm test` (unitarias; las de integración se saltan sin base). Con la rama dev: `node --env-file=.env.local node_modules/vitest/vitest.mjs run`.
- El panel del navegador integrado, cuando está oculto, no ejecuta `requestAnimationFrame`, y React deja el contenido de los `<Suspense>` sin colocar («Loading…»). No es un fallo de la app: comprobarlo con el panel visible o forzando `$RV($RB)`.
- Probar páginas con sesión sin usar la cuenta de nadie: crear en la rama dev un usuario `prueba-*` con una fila en `session` y firmar la cookie como Better Auth (`token + "." + base64(HMAC-SHA256(token, AUTH_SECRET))`, con encodeURIComponent). Con `next start` (producción) la cookie se llama `__Secure-better-auth.session_token`, también en localhost. Al acabar, borrar `prueba-%` de `grupos` y `user`, y cerrar sesión con `POST /api/auth/sign-out`: el servidor reescribe las cookies como httpOnly, y la caché de sesión mantiene viva una sesión borrada hasta 5 minutos.
- Raids en la base (fase 4): `lib/ingest/esquema.ts` (formato de subida, Zod estricto: una clave nueva en `raid.sql` obliga a ampliarlo), `lib/ingest/guardar.ts` (transacción, idempotente por grupo y slug), `lib/raids/reconstruir.ts` (vuelve a montar el `data.json`) y `lib/perfil/construir.ts` (port de `perfiles.ps1`; `redondeoNet` imita el `Math.Round` de .NET). API: `app/api/v1/grupos/[grupo]/raids/…` con sesión o token del grupo (`Authorization: Bearer dps_…`; en la base, solo su SHA-256).
- Fixtures de prueba anónimos en `tests/fixtures/`: una raid en formato v1 (el de la web estática) y otra v2, un análisis y un perfil de Claude, con los jugadores renombrados (`Veterano*`, `Jugador*`). Nunca nombres reales en el repo de pruebas.
- Páginas (fase 5): plantillas JSX en `components/{raid,jugador,grupo}/` y el código de dibujo de la web estática en `lib/legado/*.ts`, generado desde `assets/*.js` con reemplazos exactos (ADR 0003); datos de `lib/raids/vista.ts`. La web estática ya no existe: el código de `lib/legado/` se cambia directamente.
- Subida desde el navegador (fase 6): `components/subida/Asistente.tsx` y `lib/procesado/procesar.ts` (DuckDB-WASM 1.32.0). El SQL que ejecuta es `lib/procesado/sql.generado.ts`, generado desde `db/*.sql` con `npm run sql`: si se toca un `.sql`, hay que regenerarlo (una prueba lo exige). `db/runs.sql` tiene la regla del jefe principal, la misma que `extraer-raid.ps1`. Prueba de punta a punta: `node --env-file=.env.local --conditions=react-server --import tsx scripts/probar-subida.mts --run <id>` (necesita la app en localhost:3000 y `DUCKDB_EXE`). En la rama, `raid.sql` añade `servidor` a cada jugador (formato v2).
- Publicar desde el PC (fase 7): `nueva-raid.bat` → `tools/publicar.ps1` (sin git) → `tools/extraer-raid.ps1`, que escribe el JSON en `%TEMP%\dps-aion\<slug>.json` y lo devuelve como última línea. El token del grupo se crea en Ajustes y se guarda con `publicar.ps1 -Configurar` en `%APPDATA%\dps-aion\config.json` (cifrado con DPAPI); también valen `DPS_AION_API`, `DPS_AION_GRUPO` y `DPS_AION_TOKEN`. Textos de Claude: `publicar.ps1 -Analisis <carpeta-slug>\analisis.json,<…>\analisis.en.json` y `-Perfil <carpeta-jugador>\perfil.json,…` (slug = nombre de la carpeta o `-Slug`; idioma = `.en.json`). Nunca imprimas ni pegues un token. Prueba de punta a punta: `node --env-file=.env.local --conditions=react-server --import tsx scripts/probar-publicar.mts --run <id>` (app en localhost:3000; usa una copia de la base del PC y borra sus datos de prueba).
- Nombres de questlog.gg (adelantado de la fase 8): `lib/nombres/actualizar.ts` (port de `actualizar-nombres.ps1`). **questlog.gg (Cloudflare) responde 403 «Just a moment…» a las funciones de Vercel** (comprobado el 9/11/2026) y su API no tiene CORS, así que el servidor no puede bajarlos. Llegan por tres vías: (1) semilla del repo, `nombres.json` / `nombres.en.json` (apodos globales, que se sustituyen, y nombres, que solo rellenan huecos), aplicada en cada despliegue (`scripts/semilla-nombres.mts` en `build:vercel`) y en cada `actualizarNombres()`; (2) el PC: `publicar.ps1` tras cada subida (y `publicar.ps1 -Nombres` a mano, p. ej. tras subir desde el navegador) pide `GET /api/v1/grupos/:g/nombres` (ids de las raids del grupo sin nombre en algún idioma), los busca en questlog.gg y los manda con `POST` tal cual vienen (`{ es: { habilidades: { id: { name, icon } }, npcs: { id: bruto } }, en }`); el servidor les da formato (`filasQuestlog`) y solo guarda ids de raids de ese grupo; (3) descarga directa (`after()` del POST de raids, cron `/api/cron/nombres`, `npm run nombres`): en local funciona y en Vercel falla sin romper nada (queda en el resumen). Para ampliar la semilla con lo que tenga la base dev, volcar su tabla `nombres` a esos JSON. En PowerShell las variables no distinguen mayúsculas: `$s = $S.x` pisa `$S`. Los ataques que el juego llama solo «Ataque» quedan «Ataque <id>» hasta que tengan apodo. Apodos de Ludra (40, 9/11/2026, deducidos de los datos): Ludra lanza un id acabado en 0 y zonas invisibles golpean con los ids siguientes (1803230 → «Invoca la zona 11-2», 1803235 → «Impacto de la zona 11-2»); sus golpes directos se nombran por a quién dan (tanque, área, un jugador), si llevan aviso y si salen al inicio o en la fase final. Están en `apodos` de `nombres.json` / `nombres.en.json` (la semilla los aplica en cada despliegue).
- «Solicitar el análisis de mi perfil» (fase 8): el buscador de la página del grupo muestra el botón si el grupo tiene webhook de Discord (Ajustes → «Aviso en Discord», admin o más; se comprueba con Discord y se guarda cifrado con `lib/cifrado.ts`, clave derivada de `AUTH_SECRET`: si se rota, hay que volver a pegar los webhooks). `POST /api/v1/grupos/:g/jugadores/:slug/solicitar` → `lib/solicitudes.ts`: solo jugadores visibles en ese grupo, 10 min por jugador y 20 avisos/hora por grupo (tabla `solicitudes`), mensaje sin menciones en el idioma de la página. Pruebas: `tests/integracion/solicitudes.test.ts` (Discord simulado con `vi.mock`).
- Abrir a otros grupos (fase 10): `/guia`, `/privacidad` (si cambia lo que se guarda o con quién se comparte, actualizar el texto y `PRIVACIDAD_ACTUALIZADA` en `lib/sitio.ts`), pie `components/PiePagina.tsx`. Límite de 60 raids nuevas cada 30 días por grupo (`lib/limites.ts`, cuenta `raid.subir` en `auditoria`; 429 `limite-raids`). Panel `/admin/uso` solo para `SITE_ADMINS` (ids de Discord o de `user`, separados por comas; sin la variable es un 404).
- Fallos de mecánica, seguimiento y aviso de raids (9/11/2026): `db/raid.sql` saca `mecanicas` (tabla `mecanicas`; las raids subidas antes no lo traen y muestran un aviso hasta que se vuelvan a subir con `publicar.ps1 -Run … -Reemplazar`). `lib/raids/mecanicas.ts` (puro) clasifica cada ataque (da a todos / a parte del grupo / objetivo fijo / pocos datos) y compara a cada jugador con el resto; lo pinta `components/raid/Mecanicas.tsx` y va a la IA como `fallos_de_mecanica`. `lib/raids/seguimiento.ts` (puro) compara la raid con la anterior del mismo jefe (`raidAnterior` en `lib/raids/vista.ts`: en la página, solo una que quien mira vería en listados) y mide cada recomendación del análisis anterior por los ids de ataque que nombra, con cifras por intento y umbrales fijos; lo pinta `components/raid/Seguimiento.tsx` y va a la IA como `seguimiento_de_la_raid_anterior`. Las dos secciones salen del servidor (huecos `mecanicas` y `seguimiento` de `PlantillaRaid`), sin JavaScript. `lib/avisos.ts`: si el grupo tiene webhook y activa «Avisar de cada raid nueva» en Ajustes (`grupos.aviso_raids` = idioma del mensaje; se apaga al quitar el webhook), cada raid nueva manda un resumen a Discord desde el `after()` del POST, después del análisis automático. Pruebas: `tests/unit/{mecanicas,seguimiento}.test.ts`, `tests/integracion/avisos.test.ts`.
- Repaso de cada muerte (9/11/2026): `db/raid.sql` añade `repaso` a cada muerte de `detalle.<jugador>.muertes` (los 10 s anteriores: `vida_10s`, lecturas de `vida` como `[segundos, %]`, `vida_max`, los 12 últimos `golpes`, `curas` por sanador y habilidad, `escudo_10s`, `companeros`/`vivos`/`sanadores` y `defensivos` con `hace_s` y `recarga_s`); se guarda tal cual en `muertes.repaso` (jsonb). Dentro del repaso las habilidades van en la clave `hab` (no `habilidad`), para que `habilidadesPorJugador` no las cuente como del jugador. Las raids subidas antes no lo traen y muestran un aviso hasta que se resuban. `lib/raids/repaso.ts` (puro) clasifica cada muerte con umbrales fijos (de un golpe / en ráfaga / por desgaste; sin sanador vivo; con medio grupo caído; con un defensivo libre) — es una deducción, y defensivo = habilidad que el jugador castea y le pone un escudo a él mismo, con la recarga deducida del menor tiempo entre dos usos. Lo pinta `components/raid/Repaso.tsx` (hueco `repaso` de `PlantillaRaid`, sin JavaScript) y va a la IA como `repaso_de_muertes` (las cuentas y la primera muerte de cada intento; el repaso en crudo se quita de lo que se le manda). Pruebas: `tests/unit/repaso.test.ts`.
- Ventanas de daño (10/11/2026): `db/raid.sql` saca `ventanas` (`roturas` = tramos con la barra del jefe rota, de 1 s o más; `jugadores` = daño y segundos vivo dentro y fuera de las roturas, en los intentos que tuvieron alguna; `debuffs` = % del tiempo que cada jugador mantiene cada efecto sobre el jefe, en total y en rotura); se guarda tal cual en `raids.ventanas` (jsonb, migración 0006). `lib/raids/ventanas.ts` (puro) calcula el DPS por segundo vivo y cuánto sube en la rotura, y destaca a quien se aparta un 20 % del grupo solo con 3 roturas o más; lo pinta `components/raid/Ventanas.tsx` (hueco `ventanas` de `PlantillaRaid`) y va a la IA como `ventanas_de_dano`. Pruebas: `tests/unit/ventanas.test.ts`.
- Contra el mejor intento (10/11/2026): `lib/raids/intentos.ts` (puro) compara cada intento con el kill o, sin kill, con el que más lejos llegó, a igual progreso (cada 5 % de la curva: segundos y muertes acumuladas). Se separa en el primer hito con 3 muertes más o un 15 % y 10 s más lento; si no, iba igual y cayó después. Sale de `intentos`, `curva` y `detalle.*.muertes`, que traen todas las raids (no hace falta resubir nada ni tocar `raid.sql`). Lo pinta `components/raid/Intentos.tsx` (hueco `intentos` de `PlantillaRaid`, tras la progresión) y va a la IA como `comparacion_con_el_mejor_intento`. Pruebas: `tests/unit/intentos.test.ts`.
- Página del jefe (10/11/2026): `/g/<grupo>/jefes/<npc>` (`app/[lang]/g/[grupo]/jefes/[npc]/page.tsx`, `jefeParaVer` en `lib/raids/vista.ts`, mismos permisos que la página del grupo). `lib/raids/jefe.ts` (puro) junta todas las raids del grupo contra un jefe: noche a noche (mejor, mediana de los intentos de más del 5 %, muertes por intento, DPS), muro histórico (wipes por tramo de 5 % y último golpe más repetido), cronograma deducido (primer casteo de cada ataque por intento: «por tiempo» si sale casi siempre en el mismo segundo, «por vida» si al mismo %, «se repite» si el intervalo es casi fijo; contado sobre los intentos que llegaron hasta ese punto) y qué mata en cada noche. Lo pinta `components/jefe/PaginaJefe.tsx` (SVG del servidor; `GraficoAjustado.tsx`, en el cliente, solo ajusta el tamaño del texto), con «Dónde se atasca» arriba si no hay kill; la lista de jefes del grupo es `components/grupo/Jefes.tsx` (hueco `jefes` de `PlantillaGrupo`) y cada raid enlaza a su jefe (`enlaceJefe` de `PlantillaRaid`). Usa datos que traen todas las raids. Pruebas: `tests/unit/jefe.test.ts`.
